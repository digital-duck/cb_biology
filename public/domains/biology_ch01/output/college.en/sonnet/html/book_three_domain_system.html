Concept Book: Three Domain System

Biology Ch01 · Generated by SPL

Payoff

A three-domain system works because it separates what a problem means, how to reason about it rigorously, and whether the answer matches reality. Most tools live in only one of these domains: a calculator computes but does not explain; a proof assistant verifies but does not measure; a plotting library shows data but does not check logic. By deliberately routing a question through three domains — natural-language framing, symbolic or formal reasoning, and numerical or empirical verification — the system closes the loop that any single domain leaves open. This is the natural endpoint of the concept book because every earlier concept (representation, translation, proof, computation) turns out to be a partial answer to the same question: how do we know a stated idea is both logically sound and factually correct? The three-domain system is the first construction complete enough to answer that question in general, not just for special cases.

Consider how it grounds the applications this book unlocks. In symbolic algebra and computer algebra systems, the natural-language domain poses the problem, the symbolic domain manipulates expressions exactly, and the numerical domain evaluates the result to catch sign errors or domain violations a purely symbolic pass might miss. In formal proof verification, the same three-way check appears as informal conjecture, machine-checked proof, and worked numerical instances that build intuition before or after the proof exists. In scientific modeling, natural language states a hypothesis, symbolic manipulation derives its consequences, and numerical simulation tests those consequences against data — the oldest and most familiar instance of the pattern. What changes across these applications is only the vocabulary of the middle and right domains; the architecture — meaning, reasoning, verification — stays fixed.

That invariance is the payoff: once you recognize the three-domain pattern, you can build or evaluate a tool in almost any technical field by asking which domain it covers and which it is missing. A tool that only computes needs a reasoning layer; a tool that only proves needs a way to sanity-check against data; a tool that only describes needs both.

From here, pick one domain and go deeper. Scientific modeling is the most immediately practical: try formalizing a real hypothesis, deriving its symbolic consequences, and checking those consequences against a small dataset. You will feel the three domains pull against each other — and that tension is exactly what the system is built to resolve.
